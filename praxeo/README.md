# praxeo: Phase 2 thin slice

Plan §5.5 step 1: one rule family, one worked example, one historical case, run end to end. Every stage is crude. The point is that the stages connect and that scoring code exists.

```
policy.txt ──parser──▶ PolicyRecord ──context (sources before enactment)──▶ typed questions ──▶ Decider ──p per assumption──▶
clingo engine, once per reading of each unclear provision ──▶ consequences + derivations + minimal assumption sets ──▶
CR-12 combiner (subclass totals) ──▶ verifier ──▶ templated explainer ──▶ prediction.json (frozen, hashed) ──▶
outcome card opened ──▶ score.json, report.md
```

## Run

```
pip install -e '.[test]'           # pydantic, clingo, anthropic, pytest
python3 -m praxeo cases/sf_1994     # fixture parser and fixture decider (offline)
python3 -m pytest tests
```

Options: `--parser fixture|llm`, `--decider fixture|llm|human`, `--out DIR` (default `runs/…`, git-ignored), and `--thresholds PATH --fallback fixture|human|llm [--fallback-answers PATH]` to escalate low-confidence answers (example thresholds in `cases/sf_1994/thresholds.example.json`; real ones must come from the labelled question bank). The LLM parser and decider call Claude through the Anthropic SDK with structured outputs (`messages.parse` into the pydantic schema) and need `ANTHROPIC_API_KEY`. A sample offline run is committed in `cases/sf_1994/sample_run/`.

Few policy texts name related markets, so most cases need context to fill this: WE-021 gains C-13 and C-15; WE-019, WE-020 and WE-065 name none. |
| `engine.py` | symbolic engine, Configuration A (5.4) | Loads every `.lp` file in `rules/`. Writes facts (`ceiling`, `tax`, `tariff` and the actor roles the record names), opens a choice over assumptions, and labels each conclusion with its minimal assumption sets (ATMS-style). One model with every assumption held gives the derivable steps; the minimal sets of each conclusion come from clingo's subset-minimal enumeration (`domRec`), because enumerating all 2^n choices does not scale past a dozen assumptions. A consequence is reported when its most probable minimal set has every p ≥ 0.5. Where two rules give one row opposite signs, the row takes the sign of the chains that are reported (an opposing chain below the cut-off does not make it ambiguous). It runs once per reading of each unclear provision that carries `reading_facts` (clingo facts written by a person) or `reading_fields` (the Component fields a reading sets, per component, which a parser may fill; questions are asked for every reading's components, `questions.record_questions`); where the readings disagree, the consequence gets a sign per reading. Three conventions beyond `effect/7`, all optional: `group_effect/7` (a group consequence: the variables are one comma-separated string, the sign is `at_least_one_increase` or `at_least_one_decrease`), `window/2` (the conclusion is signed for a timing window, with horizon short) and `item/2` (one named item of a variable). Consequences are keyed by (actor, variable, window, item). The engine fact `announced(C)` comes from `Component.announcement_window`. Every rule stays monotone in `holds/1`: it negates only plain facts (`exception/2`, `announced/1`, `rolled_back/1`), which the minimal-set search relies on (a test checks the labels against brute force on the new rules too). |
| `combiner.py` | effect combiner (CR-12) | A declared table `COMPARISONS`. Each entry names the total's variable, the favoured and the opposed chain (by subclass suffix, variable, window or item), the dominance-premise atom (or `None` where the handbook gives none), the handbook line it comes from, and a mode. `new` forms a separate total: PC-21's keepers against the displaced (`keepers_dominate`); the landlords' resources, rent forgone against key money (`enforced`, WE-001 C-28); the first months after the effective date, PC-3 against the RS-8 raised base (no premise: ambiguous, C-21); the quality-adjusted price, lower rent against lower quality (no premise: ambiguous). `in_place` settles a capped price against the announcement-window rush with `counterfactual_catches_up` (WE-001 C-1 and C-27, A-14). A total is `ambiguous` unless the dominance premise has p ≥ 0.5; only reported chains count; a group consequence is never a chain. Not formed: a class total of turnover (PC-7 1.4 calls it a comparison, but WE-001 signs the keepers' fall and the displaced holders' rise as separate rows and gives no premise). |
| `verifier.py` | verifier | Checks every consequence. Its variable must be in the vocabulary and its actor class must have a known role (the ontology's, or one the record names). Every premise must be a record fact, an estimated assumption or an earlier conclusion. `reported` must agree with the cut-off, and per-reading signs must name existing readings. A group consequence needs two or more members, each in the vocabulary, and a group sign; a group sign on a single variable is refused; an announcement-window consequence has horizon `['short']` and a record with an announcement window. |
| `explainer.py` | templated explainer | One sentence per consequence from the derivation steps; no free text. |
| `scoring.py` | scoring (7.3, 7.4) | Headline and logic precision, recall and F1, with deduplication on (actor class, variable, horizon). Ambiguous and unverifiable predictions are excluded from precision and their counts reported. Actor classes match only when identical, because a subclass's sign can differ from its class total. It also gives the Brier score on assumptions. Group predictions (plan 7.4): verifiable if the card has a finding on any member for that actor and horizon; matched if an `effect` finding on a member has the group's direction; a false positive only if every member has a finding and each is a null or opposite; otherwise unresolved and left out of precision. Announcement-window consequences are short-horizon predictions, kept apart from the ordinary row when deduplicating; items are parts and not scored (the total is). |
| `pipeline.py` | run log | Writes and hashes the prediction before the outcome card is read. The card is optional: a fictional case has none, and its run is then not scored. |

## What the first run shows, and what it does not

Offline run on `sf_1994` (rule base 0.4; after the WE-001 widening 23 are reported, 18 of them unverifiable against the card, with the same 5 verifiable and the same scores; after windows, items and the declared comparisons 28 are reported, 22 unverifiable and 1 ambiguous, with the same 5 verifiable, headline precision, recall and F1 of 1.00 and the same Brier score; the figures below are for the first 9):
- 5 verifiable and 4 unverifiable. The unverifiable ones are the keeper and displaced subclasses, the insiders' price and the shut-out seekers' price for uncovered units.
- Headline precision 1.00, recall 1.00, F1 1.00.
- Logic F1 0.57: consequences resting on premises the card does not record drop out of the logic score.
- Assumption Brier score 0.06.
- Under 1.4 there is no excess-demand claim, because Proposition I lets the rent reset on a new tenancy. The card's citywide-rent finding is matched by the rise in initial rents.
- Rule base 0.1 had recall 0.80; the miss was F-2.

**These numbers test the plumbing. They are not evidence of accuracy.** The reasons:

1. **Contamination, and now fitting.** The patterns encoded and the fixture probabilities were chosen with knowledge of the published findings for this case. A real test needs a decider and parser that see only material dated before enactment (plan 7.2), and a held-out case. PC-21 was added to the catalog because of this case's recall miss, so this case is now development data for PC-21 and cannot test it.
2. **The outcome card is unverified.** It was written from memory of Diamond, McQuade and Qian (2019, *AER* 109(9)), because the paper could not be fetched from this environment. Every figure has to be checked against the paper, and the card has to be checked by a second person.
3. **The policy text is a summary**, not the ordinance or the ballot pamphlet.
4. **The LLM stages have not run.** There is no API credential in this environment. The code follows the SDK's documented structured-output call, but it has not been exercised against the API.
